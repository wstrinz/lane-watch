# Background identity and additional request boundary

5 September 2026. Post-handoff engineering continuation; both production launch
holds and the original exhausted epoch remain unchanged.

The native background launcher does not honor a preselected inference session
ID. Its own warning says --bg manages that identity. The prior foreground
session-header check therefore cannot justify a background binding protocol.
The gateway must be prepared under the original budget lease, wait for the
exact daemon job/session record, bind that identity without changing the lease,
and only then allow the waiting request to reach the provider.

The background client also makes additional non-streaming requests with stream
omitted. The request validator is now shared between stream and JSON transport,
accepts that standard default and preserves supported thinking/metadata fields.
Every request still reserves an explicit maximum before HTTP. No fallback,
server tool or compaction path was admitted by this change.

## Installed-client evidence

The final isolated background fixture at 13:12:44.231 UTC bound prepared lease
a32aac52-7a77-4c68-a442-5616673422d4 to daemon job a4a22414 / session
a4a22414-a654-43f1-a4fa-dabaa4d00217. The exact job receipt, unique worktree,
creation time and waiting request header agreed before the fixture release.
The binding was written before release; the original output cap/deadline stayed
unchanged. This is a fixture binding file, not a deployed runtime lease protocol.

Three requests reached the fake upstream: one stream with maximum 32,000 and
two JSON requests with maxima 1,024 each. All used the same prepared allowance.
The fake usage settled to 21 output units and 30 input units; absent cache fields
remained explicitly unreported. No real model or real credential was used.
The shapes establish additional requests, not their semantic purpose or an
explanation of the historical BS21 transcript-accounting gap.

The job was still working after the bounded response observation interval.
Completed HTTP requests are not proof that the background job has terminated.
The probe revalidated its exact job identity and stopped that fixture through
the native stop command; the recorded state became stopped. This is not a
verified deadline or descendant-process stop bound.

The retained probe sequence also records:

- --exec ignores --session-id; its environment-only fixture cannot establish
  inference-session selection. An initial global job-directory write failed
  with EPERM in the filesystem sandbox. It was moved into an isolated workspace
  config directory; no approval-review rejection occurred.
- The finite Node --exec fixture inherited its nonce but not the exact requested
  gateway URL. This does not distinguish omission from replacement or establish
  the inference environment. The inference probe uses explicit isolated settings.
- A gateway bound to the requested rather than returned session withheld all
  upstream traffic and stopped the mismatched fixture.
- Binding the actual returned session permitted the main stream; refusing the
  later non-streaming request exposed the second accounting path.

All four isolated supervisor PIDs are now absent and their rosters have no
workers. The finite Node fixture was also confirmed absent. The CLI launch/stop
handles exited, and probe-owned HTTP servers/database handles were closed.
The records and cleanup checks are in 2026-09-05-background-gateway-probes.json.

## Validation and next requirement

Twenty tests pass, 1,841 assertions, 1.443 seconds, Bun 1.3.14. TypeScript is
clean. Tests cover both native request forms sharing the budget in addition to
all prior streaming, restart, cancellation, malformed response and overrun cases.

The next production change must persist the returned daemon binding and actual
monitor-ready release against the existing launch journal and output budget.
Then verify routing and ownership for children, supervisor crash/hang behavior,
and process-tree deadline stopping. The background fixture is --bare, tool-free,
with a dummy key, isolated settings and a local fake provider. It does not prove
production subscription/profile compatibility, subagent coverage or custody App
Server enforcement. Do not enable either production adapter from this result.
